# Browser Kitty Guide

Browser Kitty の開発・運用における共通ルール、設計方針、UI/UX基準、リリース手順をまとめたガイドです。

このファイルは、個別アプリの仕様書ではなく、Browser Kitty 全体で共通して適用する判断基準として使用します。

---

# 1. Browser Kitty とは

Browser Kitty は、ブラウザだけで使える小さなツールを公開するWebサイトです。

基本的に以下の特徴を持つツールを扱います。

- ブラウザだけで動作する
- インストール不要
- ユーザー登録不要
- PC / スマートフォンの両方で利用できる
- ファイルやデータを原則として端末内で処理する
- サーバーへのアップロードを極力必要としない
- 単一HTMLとして保存・配布できることを重視する
- OSSとして公開できる構成を基本とする

Browser Kitty は「多機能な巨大アプリ」を作ることを目的としません。

特定の作業を、

**ブラウザを開いて、すぐ使えて、終わったら閉じられる**

程度の軽さで解決することを重視します。

---

# 2. 基本思想

## 2.1 ブラウザで完結させる

可能な限り、処理はブラウザ内で完結させます。

対象例:

- PDF処理
- 画像処理
- 動画処理
- 音声処理
- CSV / JSON / SQLite
- カメラ
- マイク
- WebRTC
- ONNX / WASM
- OpenCV
- Canvas
- WebCodecs
- WebGPU

サーバー処理がなくても実現できるものについては、安易にバックエンドを追加しません。

---

## 2.2 完全ローカル処理

ユーザーが読み込んだファイルや入力データについては、原則としてブラウザ内のみで処理します。

外部通信を行う場合は、その目的を明確にします。

特にユーザーファイルについて、

- 外部APIへ送信する
- サーバーへアップロードする
- クラウドストレージへ自動送信する

といった処理は、Browser Kitty の標準設計には含めません。

UI上では原則として、

**完全ローカル処理**

という表現を使用します。

ただし、実際に外部通信を行っている場合は「完全ローカル処理」と表示してはいけません。

---

# 3. 技術構成

## 3.1 基本構成

各Browser Kittyアプリは、原則として最新の `htmlapps-template` に準拠します。

基本構成の例:

```text
htmlapps-example/
├─ src/
├─ scripts/
├─ assets/
├─ dist/
├─ README.md
├─ LICENSE
├─ package.json
├─ start-local.bat
└─ ...
```

テンプレート側の構成が変更された場合は、最新テンプレートを優先します。

---

## 3.2 単一HTML

Browser Kittyでは、最終的に単一HTMLとして利用できることを重要視します。

理想形:

```text
dist/
└─ index.html
```

このHTML単体で、

- UI
- JavaScript
- CSS
- SVG
- 必要なWorker
- 必要なWASM
- 必要なモデル

などを可能な限り内包します。

ただし、サイズやブラウザ制約上、現実的でない場合は例外を認めます。

その場合でも、

**なぜ単一HTML化できないのか**

が説明できる状態にします。

---

## 3.3 外部依存

CDNから実行時にライブラリを読み込む構成は、原則避けます。

例:

```html
<script src="https://cdn.example.com/library.js"></script>
```

よりも、ビルド時に取り込みます。

理由:

- オフライン利用
- CDN障害対策
- バージョン固定
- プライバシー
- CSP
- 単一HTML化

---

# 4. ネットワーク

## 4.1 ランタイム通信

完全ローカル処理を目的とするアプリでは、実行時の外部ネットワークアクセスを原則禁止します。

確認対象:

- fetch
- XMLHttpRequest
- WebSocket
- EventSource
- CDN
- 外部フォント
- 外部画像
- telemetry
- analytics
- AI API

---

## 4.2 CSP

Content Security Policy は、必要最小限に設定します。

アプリによって以下が必要になる場合があります。

- `blob:`
- `data:`
- `wasm-unsafe-eval`
- Worker
- WebAssembly

ただし、

```text
https:
*
```

のような広すぎる許可は避けます。

# 5. UIデザイン

Browser Kittyでは、アプリごとに完全に違うデザインを作るのではなく、一定の統一感を持たせます。

---

## 5.1 ブランドカラー

基本カラー:

```text
#16624F
```

この色を、

- アクティブ状態
- 主要ボタン
- 選択状態
- アクセント
- アイコン

などに利用します。

ただし、画面全体をブランドカラーで塗りつぶすような使い方は避けます。

---

## 5.2 アイコン

UIアイコンには原則SVGを使用します。

避けるもの:

- 絵文字
- OS依存文字
- Unicode記号だけで構成したボタン

例:

悪い例:

```text
📁 ファイル
🗑 削除
⚙ 設定
```

推奨:

```text
[SVG icon] ファイル
[SVG icon] 削除
[SVG icon] 設定
```

favicon とアプリ左上のブランドアイコンは、可能な限り同一デザインにします。

# 6. PC / スマートフォン

Browser Kittyではスマートフォン対応を後回しにしません。

PC版を縮小しただけのUIにはしないことを基本とします。

---

## 6.1 スマートフォンで確認する項目

最低限以下を確認します。

- 横スクロールが出ない
- 固定ボタンが重ならない
- 下部バーがコンテンツを隠さない
- モーダルが画面外にはみ出さない
- 長いファイル名でも崩れない
- ボタンが小さすぎない
- 誤タップしにくい
- スクロール量が過剰にならない
- 主要操作が画面上部だけに集中しない

---

## 6.2 ステップ式アプリ

以下のようなアプリ:

```text
1. ファイルを選択
2. 編集
3. 出力
```

では、PCとスマートフォンでUIを分けても構いません。

PC:

```text
Step 1 → Step 2 → Step 3
```

スマートフォン:

```text
┌────────────────┐
│ Current screen │
└────────────────┘

[読み込み] [編集] [出力]
```

下部固定タブによる画面切り替えを積極的に検討します。

スマートフォンで、

**1ページに全工程を縦積みして大量スクロールさせる**

構成はできるだけ避けます。

# 7. 操作フロー

初めて使うユーザーが説明書なしで操作できることを目標とします。

---

## 7.1 最初の画面

最初の画面では、

**何をすればよいか**

が明確である必要があります。

良い例:

```text
画像を追加

JPEG / PNG をここにドロップ
または

[画像を選択]
```

悪い例:

```text
Workspace
No data loaded.
```

---

## 7.2 次の操作

現在の操作が終わったら、次に何をするか分かるようにします。

例:

```text
3枚追加しました

[並べ替える]
```

必要に応じて右下などへ次工程ボタンを配置します。

---

# 8. 状態設計

以下の状態を明確に分けます。

- 初期状態
- 空状態
- 読み込み中
- 処理中
- 完了
- 警告
- 失敗
- 一部失敗

---

## 8.1 空状態

単に、

```text
データがありません
```

と表示するだけではなく、

```text
まだ画像がありません。

画像を追加すると、ここに一覧が表示されます。

[画像を追加]
```

のように次の操作へ誘導します。

---

## 8.2 完了状態

処理が終わったら、成功したことを明確にします。

例:

```text
PDFを作成しました

12ページ
4.2 MB

[PDFを保存]
```

---

## 8.3 失敗状態

単に、

```text
Error
```

と表示しません。

最低限、

```text
画像を読み込めませんでした。

対応していない形式か、ファイルが破損している可能性があります。
```

程度の説明をします。

技術詳細は必要に応じて折りたたみ表示します。

例えば、

```text

```

ではなく、

```text

```

以下のような内容は原則として詳細情報へ入れます。

- WASM
- WebGPU
- ICE
- SDP
- WebRTC candidate
- SIMD
- WebCodecs
- tensor
- inference provider

開発者向けアプリでは例外です。

ただし、

**ユーザーが入力済みのデータをサンプルで上書きしない**

こと。

サンプルボタンは主操作より目立たせません。

# 11. ファイル読み込み

複数ファイルを扱うアプリでは、

```text
1920 × 1080
2.3 MB
JPEG
```

# 13. プレビュー

出力結果を作るアプリでは、可能な限り保存前にプレビューできるようにします。

例:

- PDF
- HTML
- 画像
- 動画
- GIF
- Contact Sheet

設定変更後の結果が重要なアプリでは、

**設定画面と実際の変換結果が乖離しない**

ようにします。

# 14. 削除

削除操作は明確にします。

重要な削除では確認ダイアログを使用します。

例:

```text

```

大量削除や復元可能な操作ではUndoも検討します。

# 15. Undo

Undoが有効な操作:

- ページ削除
- アイテム削除
- 並べ替え
- カテゴリ変更
- 完了処理

例:

```text

[元に戻す]
```

---

# 16. 保存

保存操作では、

**何が保存されるのか**

を明確にします。

悪い例:

```text

```

良い例:

```text

```



# 17. ファイル名

可能な場合は拡張子をユーザー入力から分離します。

# 18. 確認ダイアログ

以下では確認を検討します。

- データ削除
- 全消去
- 作業リセット
- 入力済みデータを上書きするサンプル
- HTML内部でのファイル保存
- 大量ファイル処理

ただし、確認ダイアログを乱用して操作を重くしません。

# 30. AI / ML

ブラウザ内AIでは、

- ONNX Runtime Web
- WebGPU
- WASM
- TensorFlow.js

等を利用して構いません。

モデル選定では、

- 精度
- モデルサイズ
- 初回読み込み時間
- 推論速度
- メモリ使用量
- スマートフォン性能

を総合的に判断します。

最高精度だけでモデルを選びません。

---

# 31. モデルサイズ

Browser Kittyでは初回利用体験を重視します。

目安として、

数MB:
非常に扱いやすい

10〜30MB:
十分現実的

50〜100MB:
用途次第

100MB以上:
明確なメリットが必要

と考えます。

# 32. 処理負荷

大量ファイル処理ではUIを固めないようにします。

必要に応じて、

- Worker
- requestIdleCallback
- 非同期処理
- バッチ処理

を使用します。

進捗を表示します。

例:

```text
37 / 120
```


ただし要確認件数が0の場合、

```text

```

のような意味のない導線を表示しません。

# 48. リリース判定

機能を増やし続けることを目的にしません。

以下が満たされていればリリースを検討します。

- 主要用途が問題なく完結する
- 初見でも使える
- 大きなバグがない
- スマートフォンで使える
- READMEがある
- スクリーンショットがある
- 単一HTMLが動く
- プライバシー説明が正しい

「追加できる機能がまだある」だけではリリースを延期しません。

# 49. 機能追加の判断

機能追加候補は以下に分けて考えます。

## 必須

ないと本来の用途を達成できない。

## リリース前に入れたい

なくても使えるが、大きくUXを改善する。

## 将来

便利だが初回リリースには不要。

この分類により、機能過多を防ぎます。

# 50. UI改善の判断

UI改善では、

**見た目を豪華にすること**

より、

**迷わず使えること**

を優先します。

判断基準:

```text
何をする画面か分かるか？
↓
次に何をすればよいか分かるか？
↓
処理結果が分かるか？
↓
間違えたとき戻れるか？
```

Browser Kittyではマーケティング臭の強い表現を避けます。

避ける例:

```text
究極の

```

推奨:

事実をそのまま説明します。

# 54. 競合との差別化

競合があること自体は問題ありません。

むしろ、

**Browser Kittyだから成立する特徴**

を考えます。

例:

- ログイン不要
- 完全ローカル処理
- 単一HTML
- オフライン利用
- 軽量
- 小さな用途に特化
- 無料
- OSS

ただし、無理に差別化機能を追加しません。

# 55. Browser Kittyらしいツール

Browser Kittyに向いているもの:

```text
入力
↓
ブラウザで処理
↓
結果を見る / 保存
```

Browser Kittyにあまり向いていないもの:

- 常時サーバーが必要
- 大規模なユーザー管理が必要
- SNS機能が中心
- 大量クラウドデータ保存が前提
- サーバー側AI API利用が中心

# 61. 最終判断

このガイドはルールを増やすことが目的ではありません。

Browser Kittyで最も重要なのは、

> ブラウザを開けばすぐ使えて、ユーザーのデータを余計な場所へ送らず、その作業をきちんと終わらせられること。

です。
